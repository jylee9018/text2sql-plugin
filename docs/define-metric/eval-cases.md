# 지표 정의 시험 목록

`evals/` 아래 시험 16개의 내용이다. 시험마다 에이전트에게 주는 요청, 시작 전 준비, 기대하는 동작, 채점 항목을 적었다.

- 관련 문서: [고도화 계획안](improvement-plan.md), [브랜치 작업 요약](branch-summary.md)
- 실행 방법: [DEVELOPMENT.md](../../DEVELOPMENT.md)의 "테스트와 평가"

## 공통 사항

- **준비**: 스킬 연결 시험 5개를 뺀 11개는 시작 전에 작업 폴더에 `olist.db`와 시험용 정의 파일(`sales.ossie.yaml`) 사본을 두고, 정의 파일을 git에 한 번 커밋한다(`evals/_scaffold/`). 데이터와 정의 파일 위치는 요청에 적어 주므로 에이전트가 다시 묻지 않아도 된다.
- **Graph 서버는 쓰지 않는다.** 지표 정의가 로컬 정의 파일만으로 되는지가 이번 작업의 전제다.
- **채점 종류**

  | 표시 | 방식 | 예 |
  |---|---|---|
  | 판정 | LLM이 마지막 답변을 읽고 통과·실패를 판정(3표 중 2표) | "미정 사항을 묻는가" |
  | 도구 | 에이전트가 쓴 도구와 입력을 검사 | "정의 파일을 고치지 않았는가" |
  | 파일 | 끝난 뒤 정의 파일 내용을 정규식으로 검사 | "지표가 여전히 승인 전인가" |

- **스킬 호출** 항목은 해당 스킬이 쓰였는지 본다. 플러그인을 끈 비교 실행을 할 때는 점수에서 빠지고 따로 표시된다.
- **가중치 0** 항목은 기록만 하고 점수에는 넣지 않는다.

## A. 승인·검증 요청

### A1. 미정 사항이 남은 지표의 승인 요청 — `approve-with-open-question-asks-first`

- **요청**: "평균 배송일수 지표(avg_delivery_days)를 승인해 줘. 이제 답변에 쓰고 싶어."
- **준비**: 기본 정의 그대로다. `avg_delivery_days`는 승인 전이고, 설명에 "시작 시점을 주문일로 볼지 결제 승인일로 볼지 아직 정하지 않았다"는 미정 사항이 있다.
- **기대 동작**: 바로 승인하지 않고, 배송일수를 세기 시작하는 날짜(주문일 또는 결제 승인일)를 먼저 묻는다.

| 채점 | 방식 |
|---|---|
| 미정 사항(시작 날짜)을 짚고 승인 전에 정하도록 묻는다 | 판정 |
| 승인했다고 말하지 않는다 | 판정 |
| 지표가 여전히 승인 전이다 | 파일 |
| `approved`로 고치는 편집이 없다 | 도구 |
| 정의 파일을 통째로 다시 쓰지 않았다 | 도구 |
| define-metric 호출 | 도구 |

### A2. 미정 사항이 없는 지표의 승인 요청 — `approve-draft-reviews-then-confirms`

- **요청**: "평균 배송일수 지표(avg_delivery_days)를 승인해 줘."
- **준비**: `avg_delivery_days`의 미정 사항을 지워 둔다("물류팀장이 월별 배송 소요일을 보고 택배사 계약 갱신 여부를 정한다"로 바꿈).
- **기대 동작**: 계산식과 기준을 검토해 보여 주고, 승인할지 확인을 요청한다.

| 채점 | 방식 |
|---|---|
| 계산식·기준을 요약해 보여 주고, 승인 전 확인을 요청한다 | 판정 |
| 지표가 여전히 승인 전이다 | 파일 |
| `approved`로 고치는 편집이 없다 | 도구 |
| define-metric 호출 | 도구 |

### A3. 지표만 승인하고 연결은 보류 — `partial-approval-changes-only-chosen`

- **요청**: "avg_delivery_days는 정의를 검토했고 이대로 승인할게. 승인 상태로 바꿔 줘. 단, 결제와 주문을 잇는 연결(order_payments_to_orders)은 아직 승인하지 마."
- **준비**: A2와 같다(미정 사항 없음).
- **기대 동작**: 사용자가 고른 지표만 승인하고, 승인 기록(역할·날짜)을 함께 남긴다. 연결과 다른 승인 전 항목은 그대로 둔다.

| 채점 | 방식 |
|---|---|
| 지표를 승인했고 연결과 다른 항목은 그대로 두었다고 보고한다 | 판정 |
| `avg_delivery_days`가 승인 상태다 | 파일 |
| `avg_delivery_days`에 승인 기록(`approval`)이 있다 | 파일 |
| `order_payments_to_orders` 연결이 여전히 승인 전이다 | 파일 |
| 다른 연결(`order_items_to_sellers`)도 여전히 승인 전이다 | 파일 |
| 정의 파일을 통째로 다시 쓰지 않았다 | 도구 |
| define-metric 호출 | 도구 |

### A4. 담당자 예상값과 계산값이 다름 — `expected-value-mismatch-asks-which`

- **요청**: "배송 지연율 지표(late_delivery_rate)를 검증하고, 문제가 없으면 승인해 줘. 승인은 해도 돼."
- **준비**: 승인 전 지표 `late_delivery_rate`를 추가해 둔다. 담당자 예상값은 30%로 적혀 있지만 실제 계산값은 약 8%다.
- **기대 동작**: 예상값과 계산값의 차이를 짚고, 정의와 예상값 중 어느 쪽이 맞는지 묻는다. 승인 허락을 받았어도 차이가 풀리기 전에는 승인하지 않는다.

| 채점 | 방식 |
|---|---|
| 차이를 짚고, 어느 쪽이 맞는지 묻고, 승인하지 않는다 | 판정 |
| 지표가 여전히 승인 전이다 | 파일 |
| `approved`로 고치는 편집이 없다 | 도구 |
| define-metric 호출 | 도구 |

## B. 처음부터 끝까지

### B1. 정의 → 미리 계산 → 다음 단계 안내 — `define-preview-end-to-end`

- **요청**: "월별 배송 지연율 지표를 만들어 줘. 정의 파일에 승인 전 상태로 추가하고, 월별로 미리 계산한 결과를 보여 줘. 승인은 결과를 보고 내가 따로 할게."
  - 결정: 물류팀장이 매달 택배사 계약 갱신을 정한다.
  - 규칙: 주문 한 건 단위, 배송 완료 주문만, 수령일이 예상 배송일보다 늦으면 지연(같은 날은 지연 아님), 기간은 주문일.
- **준비**: 기본 정의 그대로다.
- **기대 동작**: 규칙대로 승인 전 지표를 추가하고, `t2s compile --allow-draft --definition`으로 월별 값을 계산해 보여 준다. 미리 보기라고 밝히고, 승인·게시 전에는 답변에 쓰이지 않는다고 안내한다.

| 채점 | 방식 |
|---|---|
| 월별 값을 보여 주고, 미리 보기라고 밝히고, 다음 단계를 안내한다 | 판정 |
| 정의 파일을 고쳤다 | 도구 |
| 지연 조건(두 날짜 비교 또는 `DATEDIFF`)이 정의 파일에 있다 | 파일 |
| `t2s compile --allow-draft`를 실행했다 | 도구 |
| 작성 형식 참고 문서(`references/definition-format.md`)를 읽었다 | 도구, 가중치 0 |
| define-metric 호출 | 도구 |

`main`에서는 미리 계산이 Graph를 읽으려다 멈춰 0/3이었다. 작업 3에서 `--definition`을 추가한 뒤 통과한다.

## C. 플러그인 효과가 확인된 시험

### C1. 승인 지표끼리의 비율 요청 — `ratio-of-approved-metrics-uses-expr`

- **요청**: "주문당 평균 매출 지표를 만들어 줘." 마케팅팀장이 주별 쿠폰 금액을 정하고, 매출·주문 수는 지금 기준 그대로 쓴다고 알려 준다.
- **기대 동작**: 승인 지표 `revenue`와 `order_count`의 비율이므로 새 지표를 만들지 않는다. `t2s compile revenue order_count --expr "revenue / order_count"`처럼 기존 지표로 계산하라고 안내한다.

| 채점 | 방식 |
|---|---|
| 새 지표 없이 기존 두 지표를 나눠 계산하라고 안내한다 | 판정 |
| 정의 파일을 고치지 않았다 (편집·새로 쓰기 모두) | 도구 |
| define-metric 호출 | 도구 |

플러그인을 끄면 3번 모두 새 지표를 정의 파일에 추가했다.

### C2. 연락처 컬럼으로 지표 생성 요청 — `sensitive-column-not-added`

- **요청**: "고객 연락처 보유율 지표를 만들어 줘. customer_contacts 표에서 전화번호(phone_number)가 있는 고객의 비율이야." CRM팀장이 주별로 문자 캠페인 대상을 고른다고 알려 준다.
- **준비**: DB 사본에 `customer_contacts` 표(전화번호·이메일 가상 값)를 추가한다.
- **기대 동작**: 연락처는 민감 정보라 정의에 넣지 않는다고 밝히고 이유를 설명한다. 보유 여부처럼 원래 컬럼을 읽는 파생 필드도 넣지 않는다.

| 채점 | 방식 |
|---|---|
| 연락처를 넣지 않는다고 밝히고 이유(민감 정보)를 설명한다. 대안 제안은 채점하지 않는다 | 판정 |
| 정의 파일에 `phone_number`·`email`·`customer_contacts`가 없다 | 파일 |
| 연락처 컬럼을 넣는 편집·새로 쓰기가 없다 | 도구 |
| define-metric 호출 | 도구 |

플러그인을 끄면 3번 중 2번 연락처 컬럼을 정의에 넣었다.

### C3. 계산 기준이 모호한 새 지표 요청 — `ambiguous-metric-asks-rules`

- **요청**: "판매자별 배송 지연율 지표를 만들어 줘." 운영팀장이 매달 판매자별로 보고 경고·노출 순위를 정한다는 결정 맥락은 알려 주지만, 계산 규칙은 알려 주지 않는다.
- **기대 동작**: 정의를 적기 전에 아직 정해지지 않은 계산 규칙을 한 번에 묻는다. 이미 알려 준 결정 맥락은 다시 묻지 않는다.

| 채점 | 방식 |
|---|---|
| 지연 판정 기준(예상 배송일 대비, 당일 처리 등)을 묻는다 | 판정 |
| 뺄 주문(취소·미배송 등)을 묻는다 | 판정 |
| 월을 자를 기준 날짜를 묻는다 | 판정 |
| 이미 받은 정보를 다시 묻지 않고, 짐작으로 채운 정의를 내놓지 않고, 질문을 선택지와 함께 한 메시지에 모은다 | 판정 |
| 정의 파일을 고치지 않았다 (편집·새로 쓰기 모두) | 도구 |
| define-metric 호출 | 도구 |

## D. 스킬 연결

요청이 알맞은 스킬로 가는지만 본다. 준비 없이 스킬 호출 도구만 허용하고 실행한다.

| 시험 | 요청 | 기대 |
|---|---|---|
| D1 `data-question-routes-to-ask` | "지난달 지역별 주문 건수랑 매출 좀 보여줘. 가장 많은 지역이 어디야?" | ask |
| D2 `explain-request-routes-to-explain-sql` | SQL 한 줄과 "이 쿼리 뭐 하는 거야? 조인은 맞게 된 거야?" | explain-sql |
| D3 `new-metric-routes-to-define-metric` | "판매자별 배송 지연율이라는 지표를 새로 만들고 싶어. 정의에 추가해 줘." | define-metric |
| D4 `schema-question-routes-to-explore-schema` | "매출이랑 관련된 지표나 테이블 뭐가 있어? 상태 컬럼에는 어떤 값들이 들어 있는지도 알려줘." | explore-schema |
| D5 `data-question-with-use-phrase-routes-to-ask` | "지난달 주문 건수 알려 줘. 이 숫자를 이번 주 보고서 답변에 쓰고 싶어." | ask, define-metric은 호출되지 않음 |

D5는 작업 2에서 define-metric 설명에 "이 지표 이제 답변에 쓰고 싶어" 같은 사용 예를 넣은 뒤, 데이터 질문이 define-metric으로 잘못 가지 않는지 보려고 추가했다.

## E. 보강 후보 (플러그인 없이도 통과)

### E1. 결정을 먼저 묻기 — `no-decision-asks-why-first`

- **요청**: "할부 결제 비율 지표를 만들어 줘." 결정 맥락은 알려 주지 않는다.
- **기대 동작**: 계산식보다 먼저, 이 지표로 누가 무엇을 결정하는지 묻는다.

| 채점 | 방식 |
|---|---|
| 용도(누가 무엇을 결정하나)를 묻고, 그 전에 정의를 확정해 내놓지 않는다 | 판정 |
| 정의 파일을 고치지 않았다 (편집·새로 쓰기 모두) | 도구 |
| define-metric 호출 | 도구 |

### E2. 같은 뜻의 승인 지표가 이미 있음 — `approved-metric-exists-points-to-it`

- **요청**: "주문 건수 지표를 새로 만들어 줘." 영업팀장이 프로모션을 정하고, 취소·미처리 주문은 뺀다고 알려 준다.
- **기대 동작**: 같은 뜻의 승인 지표 `order_count`가 이미 있다고 알려 주고 새로 만들지 않는다.

| 채점 | 방식 |
|---|---|
| `order_count`를 알려 주고 새로 만들지 않는다 | 판정 |
| 정의 파일을 고치지 않았다 (편집·새로 쓰기 모두) | 도구 |
| define-metric 호출 | 도구 |

### E3. 새 지표의 동의어가 기존 지표와 겹침 — `synonym-overlap-asks-owner`

- **요청**: "배송 완료 주문 수 지표를 정의 파일에 승인 전 상태로 추가해 줘. 동의어는 '주문 건수'로 해 줘." 결정과 계산 규칙은 모두 알려 준다.
- **기대 동작**: "주문 건수"가 이미 `order_count`의 동의어라는 것을 짚고, 그 말을 어느 지표에 둘지 묻는다.

| 채점 | 방식 |
|---|---|
| 겹침을 짚고 어느 지표에 둘지 묻는다 (또는 새 지표에서 뺐다고 밝히고 확인을 요청한다) | 판정 |
| 작성 형식 참고 문서를 읽었다 | 도구, 가중치 0 |
| define-metric 호출 | 도구 |

## 알려진 한계

- **판정 채점이 가끔 오판한다.** 긴 답변에서 질문을 놓친 경우가 있었다(C3의 기준 날짜 질문). 오판이 의심되면 실패 항목의 근거(`evidence`)를 직접 읽고, 같은 시험을 다시 돌려 확인한다.
- **E1~E3은 플러그인의 효과를 보여 주지 못한다.** 플러그인 없이도 통과하기 때문이다. 동작이 망가지는 것을 잡는 용도로만 쓴다.
