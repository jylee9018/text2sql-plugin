# 지표 정의 에이전트(define-metric) 고도화 계획안

- 작성일: 2026-11-23
- 대상: text2sql 플러그인 0.5.1의 지표 정의 기능(`skills/define-metric`)
- 기준: `main` 브랜치 커밋 `e250ebb`
- 작업 브랜치: `improve/define-metric`

## 요약

지표 정의 에이전트로 만든 지표가 **실제 질문 답변(ask)에 쓰이지 않는 문제**를 고친다. 함께 두 가지를 한다. 에이전트가 제대로 동작하는지 **시험(evals)으로 반복 확인**할 수 있게 하고, 꼭 지켜야 하는 규칙은 **`t2s check`가 검사**하도록 옮긴다.

진행 방식: 먼저 `main`의 현재 시험 점수를 재 둔다. 이후 변경마다 그 점수와 비교한다.

## 범위와 전제

- **범위**: 지표 정의 기능(`define-metric`)과 이 기능이 쓰는 `t2s` 명령을 다룬다. 질문 답변 기능(ask)과 Graph 서버는 바꾸지 않는다.
- **전제**: 지표 정의는 로컬 정의 파일만으로 진행하고, Graph 서버는 쓰지 않는다.
  - 원칙적으로는 Graph도 확인해야 한다. 같은 지표가 이미 있는지 찾을 때 로컬 파일만 보면, Graph에는 게시됐지만 로컬 파일에는 없는 지표를 놓칠 수 있다.
  - 그래도 문제가 되지 않을 것으로 판단한다. 보통은 로컬 정의 파일(semantic-definitions 저장소)이 원본이고, Graph는 그 파일을 게시한 것이기 때문이다.
  - Graph에만 있는 지표가 생기는 운영 방식이라면(예: 서버에서 직접 수정) 이 전제가 깨진다. 그때는 지표를 찾는 단계에 Graph 확인을 추가하고, 시험 환경에 시험용 Graph 서버(mock)를 둬야 한다.
- **이 전제 덕분에**: 지표 정의 시험은 로컬 정의 파일과 DB만으로 돌릴 수 있다.

## 1. 배경: 지표 정의 에이전트의 흐름

"판매자별 배송 지연율 지표 만들어 줘" 같은 요청을 받으면 에이전트는 `skills/define-metric/SKILL.md`에 따라 다음 순서로 일한다.

1. 같은 지표가 이미 있는지 찾는다.
2. 이 지표로 누가 무엇을 결정하는지 묻는다. (예: 운영팀장이 경고를 보낼 판매자를 고른다)
3. 계산 기준을 묻는다. (예: 취소 주문은 빼는가, 며칠 늦어야 지연인가)
4. 정의 파일에 승인 전(draft) 상태로 적는다.
5. 실제 데이터로 값을 미리 계산해 보여 준다.
6. 사용자가 승인하면 승인(approved) 상태로 바꾼다.
7. 이 지표로 원래 질문에 답한다.

## 2. 현황과 문제

### 2.1 만든 지표가 답변에 쓰이지 않는다

| 단계 | 설명서가 기대하는 것 | 실제 동작 |
|---|---|---|
| 4·6. 적기·승인 | 로컬 정의 파일(`SEMANTIC_MODEL`)에 쓴다 | 로컬 파일에 쓴다 |
| 1. 기존 지표 찾기 (`t2s context`) | 로컬 정의 파일을 읽는다 | Graph 서버의 활성 모델을 읽는다 |
| 5. 미리 계산 (`t2s compile --allow-draft`) | 방금 적은 지표로 계산한다 | Graph 서버 모델로 계산한다. **새 지표는 보이지 않는다** |
| 7. 답변 (ask) | 로컬에서 승인한 지표를 쓴다 | Graph 서버만 읽는다. **게시 전까지 쓰이지 않는다** |

원인: 커밋 `0034cfb`부터 `t2s`의 조회 명령이 Graph 서버만 읽는다(`t2s/cli.py`의 `_model()`). `SEMANTIC_MODEL`은 더 이상 읽지 않는다. 로컬 파일을 읽는 명령은 경로를 직접 주는 `t2s check <파일>` 하나뿐이다. 그런데 `define-metric` 설명서는 예전 방식을 그대로 전제하고 있다.

### 2.2 지표 정의를 확인하는 시험이 없다

`evals/`에는 요청을 알맞은 스킬로 보내는지 보는 시험 4개만 있다.

| 시험 | 확인하는 것 |
|---|---|
| `data-question-routes-to-ask` | 데이터 질문이 ask로 가는가 |
| `explain-request-routes-to-explain-sql` | SQL 설명 요청이 explain-sql로 가는가 |
| `new-metric-routes-to-define-metric` | 새 지표 요청이 define-metric으로 가는가 |
| `schema-question-routes-to-explore-schema` | 스키마 질문이 explore-schema로 가는가 |

- 지표 정의 기능은 "호출되는가"만 확인한다. 질문 순서, 정의 파일 작성, 승인 처리는 시험하지 않는다.
- 4개 모두 쉬운 한 문장 요청이고 1회만 실행한다.
- 시험 안에서 DB와 정의 파일을 준비하는 장치가 없다. 그래서 `t2s`를 실제로 쓰는 시험은 만들 수 없다.

### 2.3 꼭 지켜야 하는 규칙이 설명서 문장으로만 있다

"사용자가 고른 것만 승인한다", "어떤 결정에 쓰는지 정해지지 않은 지표는 만들지 않는다", "민감한 컬럼은 넣지 않는다" 같은 규칙이 `SKILL.md`에만 적혀 있다. 스킬은 에이전트에게 주는 지시문이어서 매번 똑같이 지켜진다는 보장이 없다.

이 계획은 **반드시 지켜야 하는 규칙은 스킬이 아니라 `t2s` 코드와 테스트에 둔다**는 원칙을 제안한다. 이미 그렇게 지켜지는 규칙도 있다. SQL 안전 검사(`t2s/guard.py`)와, 승인 전 지표를 답변에 쓰지 않는 규칙(`--allow-draft` 없이는 계산하지 않음)이다. 같은 방식을 지표 정의 규칙에도 넓히자는 것이다.

### 2.4 승인 요청이 지표 정의 기능으로 가지 않는다

`define-metric`의 설명(description)은 "~ 지표 만들어줘/추가해줘/정의해줘"만 사용 예로 적고 있다. 설명서 본문에는 승인 전 지표의 미정 사항을 묻고 승인하는 절차가 있지만, "~ 지표 승인해줘" 같은 요청은 이 기능으로 가지 않는다.

시험으로 확인한 사례가 있다. 미정 사항이 남은 지표의 승인을 요청하자, 에이전트는 바로 승인하지 않고 미정 사항을 되물었다. 답은 맞았다. 그러나 `define-metric`을 쓰지 않고 정의 파일을 직접 읽어 처리했고, 플러그인 없이 실행해도 결과가 같았다. 플러그인의 승인 절차가 쓰이지 않은 것이다.

## 3. 작업

### 작업 1. 시험 환경 구축과 현재 점수 측정

- **목적**: `main`의 현재 점수를 재 두고, 이후 모든 변경을 같은 시험으로 비교할 수 있게 한다.
- **내용**:
  - 시험 준비 스크립트(`evals/_scaffold/olist.sh`): 시험마다 작업 폴더에 정의 파일(`tests/fixtures/olist/sales.ossie.yaml`)과 `olist.db`를 복사하고 `t2s` 실행 환경을 만든다.
  - 개발 안내 문서(`DEVELOPMENT.md`): 시험 실행 방법과 2.3의 원칙을 적는다.
  - 지표 정의 시험: 설명서의 분기마다 하나씩 만든다.

    | 시험 상황 | 기대하는 동작 |
    |---|---|
    | 계산 기준이 모호한 새 지표 요청 | 지연 기준, 뺄 주문, 기간을 자를 날짜를 먼저 묻는다 |
    | 미정 사항이 남은 승인 전 지표의 승인 요청 | 미정 사항을 먼저 묻고 승인을 미룬다 |
    | 미정 사항 없는 승인 전 지표의 승인 요청 | 정의를 검토한 뒤 승인 여부를 묻는다 |
    | 같은 뜻의 승인 지표가 이미 있음 | 새로 만들지 않고 그 지표를 알려 준다 |
    | 승인 지표끼리의 비율 요청 | 지표를 만들지 않고 `t2s compile --expr`로 안내한다 |
    | 어떤 결정에 쓰는지 말하지 않고 만들어 달라고 함 | 계산식보다 그것부터 묻는다 |
    | 담당자가 아는 값과 계산값이 다름 | 어느 쪽이 틀렸는지 묻는다 |
    | 지표만 승인하고 연결은 보류 | 사용자가 고른 것만 승인 상태로 바뀐다 |
    | 새 지표의 동의어가 기존 지표와 겹침 | 어느 지표에 둘지 묻는다 |
    | 연락처 컬럼으로 지표 생성 요청 | 그 컬럼을 넣지 않는다 |
    | 데이터 질문에 "답변에 쓰고 싶어"가 들어감 | `define-metric`이 아니라 ask로 간다 |
    | 정의 → 미리 계산 → 승인 → 게시 안내 | 로컬 정의 파일만으로 처음부터 끝까지 이어진다 |

  - 기존 시험 4개는 지금 형식(`prompt.md`와 채점 파일)도 시험 도구가 지원하므로 그대로 둔다.
  - 채점은 LLM 판정만 쓰지 않는다. 시험마다 파일 변경 여부나 도구 호출 여부처럼 결과가 분명한 항목을 하나 이상 둔다.
  - `main`의 스킬을 바꾸지 않은 상태로 전체 시험을 시험마다 3회씩 실행한다. 플러그인을 끈 비교 실행도 함께 돌린다.
    - 3회씩 재는 이유: 같은 요청도 실행마다 결과가 달라질 수 있다. 1회 측정으로는 이후 변경의 효과와 우연을 구분할 수 없다.
    - 비교 실행을 하는 이유: 플러그인 없이도 통과하는 시험은 플러그인을 지키는 효과가 약하다. 이런 시험을 가려 남길지 정한다.
  - 시험을 두 가지로 나눠 쓴다.
    - **고칠 대상**: 지금 실패하거나 흔들리는 시험. 작업 2·3의 효과를 볼 때 3회씩 잰다.
    - **지킬 대상**: 지금 잘 되는 동작을 확인하는 시험. 작업마다 1회씩 돌려 망가지지 않았는지 본다. 작업 5(`SKILL.md` 정리)에서는 전체를 3회씩 다시 잰다.
- **결과**: [현재 점수](eval-baseline.md)에 기록했다.
- **완료 기준**: 모든 시험의 3회 점수와 비교 실행 점수가 기록되고, 시험마다 고칠 대상인지 지킬 대상인지 정해진다. 2.1·2.4 때문에 실패하는 시험이 있는 것이 정상이다. 그 실패를 작업 2·3에서 고친다.

### 작업 2. 승인 요청이 지표 정의 기능으로 가게 하기

- **목적**: 2.4. "~ 지표 승인해줘" 같은 요청도 지표 정의 기능의 승인 절차를 따르게 한다.
- **내용**: `define-metric`의 설명(description)에 두 가지를 추가한다. 승인 전 지표를 검토·승인할 때도 쓴다는 것, 그리고 "~ 지표 승인해줘", "이 지표 이제 답변에 쓰고 싶어" 같은 사용 예다.
- **완료 기준**: 승인 관련 시험에서 `define-metric`이 쓰인다. "답변에 쓰고 싶어"가 들어간 데이터 질문 시험과 기존 시험 4개는 작업 1의 점수보다 떨어지지 않는다.

### 작업 3. 정의를 읽는 곳 정리

- **목적**: 2.1. 새로 만든 지표를 바로 미리 계산할 수 있게 하고, 승인 뒤 답변에 쓰이기까지의 절차를 분명히 한다.
- **내용 (권장안)**:
  - `t2s context`·`schema`·`values`·`compile`·`sql`에 `--definition <파일>` 옵션을 추가한다. `schema`·`values`는 계산 규칙을 정할 때 실제 코드값을 확인하는 데 쓰이고, 지금은 Graph 서버 토큰이 없으면 멈춘다. 이 옵션이 있을 때만 로컬 파일을 읽고, 없으면 지금처럼 Graph 서버를 읽는다. 출력에는 어디서 읽었는지(`source: local` 또는 `graph`)를 표시한다.
  - `SKILL.md`의 1·5·7단계 명령이 모두 `--definition <파일>`을 쓰도록 고친다. 그러면 지표 정의는 Graph 서버 없이 로컬 정의 파일과 DB만으로 진행된다.
  - 로컬에서 승인하는 것은 "게시 준비 완료"를 뜻하게 한다. 답변에 쓰이는 시점은 Graph 서버에 게시된 뒤라고 안내하고, 게시 절차를 알려 준다. 게시 전에 결과가 필요하면 "미리 보기, 아직 게시 전"이라고 표시해 보여 준다.
- **대안**: Graph 서버에 승인 전 지표를 올리는 기능을 추가하고, 미리 계산과 승인을 서버에서 처리한다. 흐름은 가장 단순해지지만 서버(text2sql-graph-mcp)와 권한 모델을 바꿔야 한다.
- **완료 기준**: `tests/test_cli.py`에 옵션 테스트를 추가한다. "처음부터 끝까지" 시험이 통과하고, 다른 시험은 작업 1의 점수보다 떨어지지 않는다.

### 작업 4. 규칙 검사를 `t2s check`로 옮기기

- **목적**: 2.3. 에이전트가 규칙을 놓쳐도 잘못된 정의가 남지 않게 한다.
- **내용**: `t2s check`에 아래 검사를 추가한다. 정의 파일을 고칠 때마다 훅(`hooks/check_definition.py`)이 `t2s check --static`을 실행하므로, 검사를 추가하면 편집 직후 바로 걸린다.

  | 규칙 | 검사 |
  |---|---|
  | 사용자가 고른 것만 승인 | 승인된 지표에 승인 기록(`approval: {by: <역할>, at: "<날짜>"}`)이 없으면 경고 |
  | 어떤 결정에 쓰는지 정해진 지표만 | `decision`이 비어 있거나 모델의 `decisions`에 없는 id면 경고 |
  | 고칠 때마다 `revision` 증가 | 내용이 바뀌었는데 `revision`이 같으면 경고 |
  | 민감 컬럼 금지 | 연락처·계좌번호·카드번호·주민번호 같은 이름이 보이면 경고 |

- **완료 기준**: `tests/test_definition.py`에 규칙마다 통과·실패 사례를 추가한다. 시험 점수는 작업 1보다 떨어지지 않는다.

### 작업 5. `SKILL.md` 정리

- **목적**: 설명서를 짧게 만들어 에이전트가 핵심 순서를 놓치지 않게 한다. 지금 144줄이다.
- **내용**: 작업 4에서 `t2s check`가 맡게 된 세부 규칙과 정의 파일 작성 형식을 `references/definition-format.md`로 옮긴다. `SKILL.md`에는 단계별 순서와 "필요할 때 참고 문서를 읽는다"는 안내만 남긴다.
- **완료 기준**: 정리 전과 후의 시험 점수를 비교해, 떨어지지 않을 때만 반영한다.

| 4 | 규칙 검사를 `t2s check`로 옮기기 | 작업 1, 결정 2 |
| 5 | `SKILL.md` 정리 | 작업 1·4 |

- 시험(작업 1)을 가장 먼저 한다. 현재 점수를 재 둬야 이후 변경이 나아졌는지 판단할 수 있다.
- 작업 2·3·4는 서로 독립적이라 순서를 바꿔도 된다.
- 작업마다 따로 커밋해서, 점수 변화가 어느 변경 때문인지 구분되게 한다.

## 5. 결정이 필요한 사항

1. **정의를 읽는 곳 정리 방식(작업 3)**: 권장안(플러그인에 `--definition` 옵션 추가)과 대안(Graph 서버에 기능 추가) 중 무엇으로 할지. 대안을 고르면 서버 담당자와 상의해야 한다.
2. **승인 기록 형식(작업 4)**: 승인한 사람을 역할로만 적을지(지금 정의 파일의 다른 기록과 같은 방식), 계정까지 적을지.
3. **전제 확인**: "로컬 정의 파일이 원본이고 Graph는 게시본"이라는 운영 방식이 맞는지. 맞지 않으면 작업 3에 Graph 확인 단계를, 작업 1에 시험용 Graph 서버를 추가한다.

## 6. 참고

### 시험 실행 비용

`claude plugin eval`은 시험마다 별도의 Claude 세션을 실행해 문제를 풀게 하고, 일부 항목은 다른 Claude가 채점한다. 1회에 $0.13~0.21 정도가 든다. 시험 형식을 확인할 때는 1회만 실행하고(`--runs 1`), 결과를 판단할 때는 시험마다 3회씩 실행한다. 코드 테스트(`uv run pytest`)는 로컬에서만 돌기 때문에 비용이 들지 않는다.

### 작업 브랜치에 미리 해 둔 것

`improve/define-metric` 브랜치에 작업 1·2의 일부가 들어 있다.

| 항목 | 해당 작업 |
|---|---|
| `DEVELOPMENT.md`, `scripts/dev.sh` (개발 환경 안내와 실행 스크립트) | 작업 1 |
| 시험 준비 스크립트 `evals/_scaffold/olist.sh` | 작업 1 |
| 시험 "계산 기준이 모호한 새 지표 요청", "미정 사항이 남은 승인 전 지표의 승인 요청" | 작업 1 |

작업 1에서 현재 점수를 잴 때는 설명(description) 수정을 빼고 `main`의 스킬 그대로 잰다.
